# PRD — GitHub Issue AI 自动化开发流水线

## 1. 产品概述

### 1.1 背景

开源社区每天产生大量有价值的 Issue，但人工筛选、开发、提交 PR 的完整链路耗时极长。本产品通过多智能体流水线，将"发现 Issue → 价值评估 → 代码开发 → 代码评审 → 提交 PR"全链路自动化，人工只在关键决策节点介入。

### 1.2 目标用户

个人开发者 / 小型技术团队，具备：
- 一定的开源贡献意愿
- GitHub 账号及基本权限
- 愿意通过 AI 提升开源贡献效率

### 1.3 核心价值

| 维度 | 传统方式 | 本产品 |
|------|----------|--------|
| Issue 发现 | 手动浏览 | 自动抓取 + AI 筛选 |
| 价值判断 | 主观经验 | 多维度量化评分 |
| 代码开发 | 全人工 | AI 开发 + 自测 |
| 代码评审 | 等待他人 | AI 预评审 + 人工把关 |
| PR 提交 | 手动操作 | 全自动 |

## 2. 功能范围

### 2.1 核心功能（MVP）

#### F1 — Issue 抓取服务
- 定时抓取目标 GitHub 仓库/话题下的 open Issues
- 支持配置：目标仓库列表、编程语言过滤、Topic 标签、Star 数门槛、Issue 标签
- 支持 GitHub Trending 自动发现 + 手动指定仓库两种来源
- 去重：相同 Issue 不重复入库
- 抓取结果写入数据库，推入评估队列

#### F2 — Issue 价值评估（Agent A）
- 并发多实例从队列消费
- 输出结构化评估报告（评分 + 维度分析 + 推荐理由）
- 支持配置不同模型（多厂商 API）
- 评估完成后 Issue 状态变更为 `PENDING_DECISION`

#### F3 — 看板（Dashboard）
- Issue 列表：筛选、排序、搜索
- Issue 详情：原始内容 + Agent A 评估报告 + 外链跳转
- 操作：忽略 / 加入开发队列
- 状态看板：各状态 Issue 数量统计
- 开发进度：实时查看 Agent B 执行日志
- 抓取日志：查看 Crawler 运行历史
- PR 状态：已提交 PR 的状态追踪

#### F4 — 代码开发（Agent B）
- 并发多实例从开发队列领取任务
- Fork 目标仓库 → Clone → 分析代码库 → 制定方案 → 实现变更 → 运行测试 → 自测
- 运行在 Docker 隔离容器中
- 支持配置不同模型
- 完成后推入评审队列

#### F5 — 代码评审（Agent C）
- 并发多实例从评审队列领取任务
- 多维度评审：正确性、测试覆盖、代码风格、安全性、PR 描述质量
- 通过 → 提交 PR；不通过 → 附评审意见退回开发队列
- 支持配置不同模型

#### F6 — PR 提交与追踪
- 自动构建标准 PR 描述（问题描述、解决方案、测试说明）
- 提交到目标仓库
- 监听 PR 状态变化（merge / close / comment）
- PR 被关闭/拒绝 → 进入人工审核节点

### 2.2 配置管理（项目配置文件，非 UI）
- 抓取目标（仓库列表、话题、筛选条件）
- 模型配置（各 Agent 使用的模型及 API Key）
- GitHub 账号配置
- 并发数、超时、重试策略

### 2.3 非目标（Out of Scope）

- UI 内嵌配置管理页面
- 多用户 / 团队权限管理
- 支付 / 订阅功能
- 自动合并（merge 由仓库 maintainer 决定）
- 移动端适配

## 3. 用户故事

### 3.1 Issue 发现与筛选

```
作为开发者
我希望每天早晨看到一批 AI 筛选后的高价值 Issue
以便我快速决定是否投入开发时间
```

**验收标准：**
- 看板默认展示评分 ≥ 7/10 的 Issue
- 每条 Issue 显示：仓库名、Star 数、Issue 标题、评分、工作量估算、推荐理由
- 支持按评分/工作量/仓库排序
- 点击 Issue 标题可跳转到 GitHub 原页面

### 3.2 开发任务管理

```
作为开发者
我希望在看板上选择 Issue 加入开发队列
并实时看到 Agent B 的开发进度
以便我了解当前自动化开发的状态
```

**验收标准：**
- 点击"加入开发"后 Issue 状态立即变为 `QUEUED_DEV`
- 看板开发中区域显示：当前任务、已完成步骤、预计剩余时间
- 可查看 Agent B 的实时执行日志（clone、分析、修改、测试）

### 3.3 PR 闭环

```
作为开发者
当 PR 被 maintainer 关闭时
我希望在看板上看到关闭原因
并能选择是否重新开发
```

**验收标准：**
- PR 关闭后看板出现通知，显示 PR 链接和关闭原因摘要
- 提供"归档"和"重新开发"两个操作
- 选择"重新开发"后 Issue 带上历史上下文重新进入开发队列

## 4. Issue 状态定义

| 状态 | 中文 | 触发条件 |
|------|------|----------|
| `DISCOVERED` | 已发现 | Crawler 抓取到 |
| `ANALYZING` | 评估中 | Agent A 领取任务 |
| `PENDING_DECISION` | 待决策 | Agent A 评估完成 |
| `IGNORED` | 已忽略 | 用户选择忽略 |
| `QUEUED_DEV` | 待开发 | 用户选择开发 |
| `IN_DEV` | 开发中 | Agent B 领取任务 |
| `DEV_TESTING` | 自测中 | Agent B 运行测试 |
| `QUEUED_REVIEW` | 待评审 | Agent B 自测通过 |
| `IN_REVIEW` | 评审中 | Agent C 领取任务 |
| `REVIEW_REJECTED` | 评审退回 | Agent C 不通过 |
| `PR_SUBMITTED` | PR 已提交 | PR 创建成功 |
| `PR_MERGED` | PR 已合并 | GitHub Webhook |
| `PR_CLOSED` | PR 已关闭 | GitHub Webhook，进入人工审核 |
| `ARCHIVED` | 已归档 | 用户选择归档 |

## 5. 成功指标

| 指标 | 目标 |
|------|------|
| Issue 筛选精准率 | 用户采纳开发率 ≥ 30% |
| Agent B 自测通过率 | ≥ 70% |
| Agent C 通过率（进入 PR） | ≥ 60% |
| PR 被 maintainer merge 率 | ≥ 20%（受外部因素影响） |
| 全链路端到端时间 | 发现到提交 PR ≤ 2 小时 |
